## THE ARGUMENT THAT NEEDS NO ORACLE

Look at the probe pool's stake at 305 and at 306:

  305   1,730,597,146,933
  306   1,730,595,594,678
  diff          1,552,255   =  0.00009%

These are supposed to be DIFFERENT snapshots a FULL EPOCH apart — 305's leadership stake is the end
of epoch 303, 306's is the end of epoch 304. Cardano's own data shows this pool's stake moving
~0.06% per epoch. **Two independently derived snapshots one epoch apart cannot agree to nine
significant figures. That is a copy, not a derivation.**

The pool SET was rebuilt correctly at 306 (446 -> 505 entries, +57 zero-stake, matching the shape of
cardano's own nesPd, which carries 505 pools and 57 zero-sigma entries at epoch 310). It is the
STAKE VALUES that did not advance.

## DIAGNOSIS

**The first native leadership freeze reproduces the bootstrap-imported stake instead of deriving the
end-of-epoch-304 mark snapshot.** By the second native freeze the derivation is correct and matches
cardano to five significant figures.

Direction and magnitude both fit: a stale, seed-era denominator that is ~4% too high deflates every
pool's sigma by ~2.9%, which lowers every leader threshold by ~2.9%. Ade then rejects exactly those
headers whose VRF value falls in the resulting narrow band — which is why the node followed thousands
of blocks before hitting one, and why it hits the SAME one every time. Only +0.0315% of sigma was
needed for this header; the available correction is ~2.9%, so the fix clears it with margin.

Call site: `cross_epoch_boundary_with_effect` -> `FrozenLeadershipPoolDistr::from_boundary_snapshot`
(`epoch_accumulator.rs:877`), whose `mark_pool_stakes` come from `cross_epoch_boundary_transition`'s
inputs — built from the point-bound base-UTxO stake at the mark source `s_prev`. For the first native
crossing, `s_prev` is 130,118,358 and the reduced checkpoint reaching it was itself replayed forward
from the Mithril seed anchor at 129,813,427. That is where the staleness has to be, and it is the
next thing to instrument.

## CORRECTION, same day, before anyone acted on the above. TWO CLAIMS WITHDRAWN.
################################################################################

The pairwise pool-by-pool diff that should have been run BEFORE the sections above
refutes their central argument.

### WITHDRAWN 1 — "that is a copy, not a derivation"

The argument rested on the probe pool's stake agreeing to 0.00009% between epochs
305 and 306, across snapshots a full epoch apart. Measured across the WHOLE
distribution rather than one pool:

  305 -> 306 : 412 of 446 shared pools BYTE-IDENTICAL   (92.38%)
  306 -> 307 : 425 of 504 shared pools BYTE-IDENTICAL   (84.33%)

Epoch 307 is the KNOWN-CORRECT derivation — it matches cardano to five significant
figures — and it too leaves 84% of pools byte-identical. **High byte-identity
between consecutive epochs is NORMAL on this chain**; preprod delegation is largely
static. One pool cannot characterise a distribution, and the distribution was one
command away.

### WITHDRAWN 2 — "the first native freeze reproduces the bootstrap stake"

Follows from the above, and is withdrawn with it.

### WHAT THE DIFF ACTUALLY FOUND — one membership entry carries the whole anomaly

  306 -> 307:  79 pools moved, sum|delta| =    885,389,101,338
               DENOMINATORS differ by       62,479,359,742,957      (a 70x mismatch)

  ONLY IN 306: pool 8ed5ab11e76094fa2a2ab29fc3a57498d07e68f6fde6f326162eea88
               stake 63,075,223,742,053  = 3.879% of the epoch-306 denominator

  Presence:
    305 (bootstrap-IMPORTED = cardano's own calculatePoolDistr)  66,525,197,762,769
    306 (first native freeze)                                    63,075,223,742,053
    307 (second native freeze)                                   ABSENT
    cardano nesPd at epoch 310 (bech32-checked, 2 controls)      ABSENT

  `cardano-cli query pool-state` returns `{}` — the pool is RETIRED.

Removing it from the epoch-306 denominator raises the issuer's sigma from
0.10642836% to 0.11072%, a **+4.03%** move, where **+0.0315%** was required.

### WHY THIS IS STILL NOT A FIX — the rule is not established

That pool is in the BOOTSTRAP-IMPORTED 305 distribution, i.e. cardano's OWN output,
so cardano did carry it at seed+1. If it retired at the boundary into 306, epoch
306's leadership — frozen at the 304->305 crossing — may LEGITIMATELY include it,
exactly as `from_boundary_snapshot` documents.

Which puts the defect one level down:

  Ade      `to_pool_distr_view`: total_active_stake = SUM OF THE POOLDISTR ENTRIES
  cardano  `calculatePoolDistr`: divides by `sumAllStake stake` — the SNAPSHOT's
           total, INDEPENDENT of which pools are in the map.

Under cardano's definition a retiring pool cannot move the denominator at all.
Under Ade's it moves it by that pool's entire stake. That has exactly the observed
shape, and it also explains why 307 matches: no membership change there to expose
it.

### ENTRY OBLIGATION — answer before touching any code

  (a) Does cardano's nesPd for epoch E include a pool that retires at the boundary
      into E-1?
  (b) Is the leader-check sigma denominator the sum of the PoolDistr entries, or the
      snapshot's total stake?

(b) is decisive: if it is the snapshot total, Ade's membership rule stays exactly as
it is and only the denominator derivation changes.

Both are cardano-ledger RULES questions that block bytes cannot settle — the BND-2
shape, whose ruling was "establish what cardano-ledger does FIRST; do not change the
guard before that." **ORACLE EXTRACTION is the next step, not a code change.**

**Do NOT drop the pool to make the header pass.** Until (b) is answered that is
indistinguishable from weakening a gate to make a test go green.
