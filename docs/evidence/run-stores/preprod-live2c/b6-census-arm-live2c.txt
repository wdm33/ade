## WHY THE STARVATION IS SELF-SUSTAINING (the B6 mechanism, now named)

  measured block arrival at tip, from the census itself:
      95.0s / 8 blocks = 11.9 s per block
     115.2s / 6 blocks = 19.2 s per block
      89.8s / 3 blocks = 29.9 s per block

  A pass costs ~90-133s, dominated by a fixed ~80-115s co-advance. Blocks arrive every ~12-30s. So
  3-9 blocks ALWAYS queue while a pass runs, has_work_ready() is therefore true every time the
  planner is consulted, and the planner returns SyncOnce forever. NoWorkReady -- the state a
  ForgeTick requires -- is unreachable while the pass costs more than the block interval.

  That is why waiting longer cannot produce a ForgeTick, and it is a design-level condition rather
  than an unlucky run: the loop cannot outrun the chain while it pays a fixed six-figure-millisecond
  cost per pass.

  Implication for the B6 slice (NOT designed here): the lever is the FIXED cost, not the deferral
  policy. Any change that makes the co-advance proportional to work admitted -- or amortises it --
  drops a tip pass toward the ~10-20s sync cost, which is below the block interval, at which point
  NoWorkReady becomes reachable without touching the deferral rule at all.

back-to-back A/B from the frozen state is still the way to settle it -- the frozen store is kept
for exactly that.
