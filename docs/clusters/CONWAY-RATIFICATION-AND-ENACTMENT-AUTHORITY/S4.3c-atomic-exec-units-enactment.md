# S4.3c — atomic exec-units parameter-change enactment (the single authority slice)

## The slice

A supported ratified exec-units `ParameterChange` produces a COMPLETE governance/pparams delta applied in one
constructed boundary result — OR a structured `GovernanceTerminal` with ZERO mutation. This is the deliberate
activation the whole S4.3 arc prepared: S4.3a gave one boundary authority (`plan_conway_governance_epoch`),
S4.3b gave source-bound V11 state + the closed full-`[mem,steps]` update decoder, the capstone proved the
grammar + the store live. S4.3c turns the `PotentiallyRatifiable` terminal into an atomic enactment for exactly
the exec-units subset, and a fail-closed terminal for everything else.

Governed by [[feedback_enactment_is_atomic_no_split_effects]] + [[feedback_versioned_authoritative_state_no_fabricated_default]].

The S4.4 anchor already proved only `69c948cd` RATIFIES at 1095 (the five siblings lack the votes); they leave

## Hard boundaries (binding)

1. **Closed subset only.** Support only a `ParameterChange` whose decoded update touches ONLY `maxTxExUnits`
   (key 20) and/or `maxBlockExUnits` (key 21), each with `steps` UNCHANGED vs the current bound value. Anything
   else ratified → `UnsupportedRatifiedAction`, zero mutation.
2. **`Unversioned` current state is a hard terminal.** If `max_block_ex_units` or `prev_pparam_action` is
   `Unversioned` on the boundary state, the enact path returns a `GovernanceTerminal` — NEVER a fallback/fabricated
   value. (A pre-V11 store reaching the enact path is a miswire.)
3. **Bound nesting/size before decoding** the opaque `update` bytes (the BLUE security S4.3c watch-item): cap the
   byte length and CBOR nesting depth before `decode_exec_units_param_update` runs on attacker-influenced bytes.
4. **Full RATIFY, not thresholds.** Before planning enactment, verify the full acceptance conditions, not just
   `check_ratification` (which is thresholds-only, renamed-in-spirit `ThresholdsAccepted`):
   - **prev-action lineage**: the proposal's `prev_action` == the current `prev_pparam_action` root (Enacted id
     or NoPreviousAction). A mismatch ⇒ not ratifiable (carry), never enact.
   - the required voting bodies actually accept (committee + DRep + SPO for a security-group exec-units change);
   - no delaying action already accepted this boundary;
   - (treasury sufficiency: N/A — exec-units carry no withdrawal.)
   Threshold success alone is NOT enough.
5. **One constructed boundary result** carries, atomically:
   - the new Tx/block memory limits (`PParamsDelta::Set`, steps preserved);
   - the advanced previous-pparam-action root (`PrevPParamActionDelta::Set(winner id)`);
   - ALL removals with explicit `RemovalCause` (`Enacted` for the winner, `PrunedByEnactment` for the superseded
     siblings; `Expired` still handled as before);
   - every matching `DepositReturn` (registered → reward account, deregistered → treasury, none → NoDeposit);
   - the resulting proposal forest/map (the winner + its pruned subtree removed, order preserved).
6. **Fail-closed, zero partial mutation.** Any unsupported ratified action, changed steps, malformed update,
   missing previous-action state, or an unexplained removal ⇒ a `GovernanceTerminal` computed BEFORE any mutation.
   **At most ONE action enacts per boundary**: a ratifiable child chaining onto the winner halts
   (`ChainedEnactment`), and MORE THAN ONE ratifiable sibling of the current root halts
   (`CompetingRatifiableActions`) — cardano-ledger enacts the submission-first (OMap-order) sibling, which Ade
   cannot reconstruct from canonical state, so it fail-closes rather than pick the GovActionId-first and risk a
   silent divergence. Both are symmetric fail-closes; multi-enactment is a later slice.
7. **Scope fence.** NO broader parameter changes, committee effects, treasury withdrawals, constitutions, or hard
   forks in this slice. Those stay `UnsupportedRatifiedAction`.

## Where it changes the code

- **`governance.rs` `plan_conway_governance_epoch`**: the `thresholds_accepted` branch (today → `PotentiallyRatifiable`)
  becomes: run full RATIFY; if the winner is a supported exec-units `ParameterChange` with unchanged steps →
  build the enactment (decode its update, compute the pparams Set, the root Set, the enacted+pruned removals +
  their deposit returns); else → `UnsupportedRatifiedAction`. Enacts AT MOST ONE action per boundary: prune ONLY
  the winner's LOSING-sibling subtrees (proposals sharing the winner's parent root + their descendants), NEVER
  the winner's OWN descendants — a child chaining onto the winner is the new lineage, not a loser. A ratifiable
  child chaining onto the winner (`prev_action` == winner) halts as `UnsupportedRatifiedAction { ChainedEnactment }`
  (multi-enactment is a later slice); a pending (non-ratifiable) chain child is CARRIED, its deposit left escrowed
  (pruning it would silently diverge the proposal set + deposit pot from Conway). Emit `PParamsDelta::Set` /
  `PrevPParamActionDelta::Set`.
- **`rules.rs` `apply_epoch_boundary_with_registrations`** (the single application point): APPLY `plan.pparams`
  (Set → write the two memory limits onto `ProtocolParameters`, steps untouched) and `plan.prev_pparam_action`
  (Set → the new `ConwayGovState.prev_pparam_action`). Today the applier IGNORES both (correct while S4.3a keeps
  them `Unchanged`; the S4.3a BLUE review flagged this as the S4.3c wire-up). Still one atomic construction.
- **`state.rs` / helpers**: `plan_conway_governance_epoch` needs the current `max_block_ex_units` +
  `prev_pparam_action` as inputs (to verify steps-equality + lineage). Thread them into
  `ConwayGovernanceEpochInput`.
- Reuse `decode_exec_units_param_update` (S4.3b) + `apply_update`'s field-application half for the memory limits.

Sequencing: land the hermetic gates + the corpus differential GREEN, THEN use the Preview node (still up) as a
LIVE confirmation — not the first discovery mechanism.

## What S4.3c does NOT do

Other action kinds' enactment (treasury/hard-fork/committee/constitution) → each its own later slice; the
byte-exact InstantStake/psDRepDistr DRep basis → S6. Multi-enactment (competing siblings / chains) → a later
slice (fail-closed here). The exec-units deposit refunds (the enacted winner + its pruned siblings) reuse the
oracle-proven CPDE deposit-return path (registered → reward account, deregistered → treasury); Ade tracks no
separate deposit/obligations pot, so a refund is a direct reward/treasury credit that matches the oracle's
observable outputs (the CPDE −500B closure proved treasury/reserves Δ match with pots untouched). A FULL-LEDGER
ADA-conservation differential of the enactment vs the real epoch-1096 pots awaits the B3c-unblocked byte-exact
differential — the corpus gate asserts the enactment PLAN (six 100k refunds), not the total-supply
reconciliation. This slice is the exec-units subset only.
